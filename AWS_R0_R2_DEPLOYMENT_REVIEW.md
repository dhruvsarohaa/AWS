# AWS R0–R2 deployment review

Initial review 10 October 2026; final deployment-readiness and scope review updated **11 October 2026 IST**. **No AWS login, account inspection or provisioning was performed in this review.** This records local code and infrastructure findings before the final deployment step. It is not evidence of a deployed URL, current account credits or cloud permissions.

## Recommended release scope

Ship the verified local R0/R1/R2 planner with regional forecasts, bounded nearby observations, historical evidence, local planning storage and offline recovery. R3 shared accounts, scheduled email, public evidence/widget, weather and satellite-fire context remain paused. R4/R5 remain deferred.

The existing stack uses Amplify static hosting, API Gateway REST with regional WAF, read/ingestion/dispatcher Lambdas, SQS refresh buffering, DynamoDB, a private S3 archive, Secrets Manager and compact CloudWatch monitoring. EventBridge Scheduler checks refresh demand every five minutes. This is an appropriate bounded pilot; it is not unrestricted India-wide concurrency.

## Scope findings and implemented corrections

At the start of this review, `template.yaml` always provisioned Cognito, SES configuration/delivery feedback resources and notification queues/Lambdas, even though email/context/public capability flags defaulted off. Turning off optional UI flags alone did not remove the R3 infrastructure or endpoint surface.

The corrected template now defaults `ReleaseScope` to `R0R2` and `SharedWorkspacesEnabled` to false. Three Cognito resources require both `Full` scope and explicitly enabled staff workspaces; a CloudFormation rule rejects shared workspaces under the default scope. Eleven notification/SES/feedback resources additionally require explicitly enabled email and a sender. Optional environment variables, policies and outputs are conditional. The operator SNS topic requires an alert email, and all four alarm actions are conditional. A supplied restored table suppresses creation of a second evidence table. `scripts/check-infra.mjs` passed local assertions for those 14 conditioned R3 resources, the optional operator topic/alarm actions, disabled defaults, conditional variables/outputs, restored-table behavior, release-scope guard and the 20–40 station bound. `sam validate --lint` and the PowerShell AST check also passed locally. These checks do not create an AWS stack.

The deployment script now defaults `ReleaseScope` to `R0R2`. Its scoped gate currently selects **24** baseline/R0/R1/R2/OpenAQ/release-scope test files, including the new offline-storage and accessibility regressions, and excludes R3/R4/R5, workspace and pilot integration suites. Selection is computed from the test directory, so the count can change as scoped regressions are added. It runs the scoped gate, build, lint and infrastructure/configuration checks before cloud identity or provisioning. Local guard checks confirmed that `-Weather` is refused in the default scope and that `-ReviewEmail` cannot be enabled without shared workspaces in `Full` scope; these checks exited before CLI execution or loading the secret file.

Eight release-scope regressions passed: unknown/missing scope fails closed to `R0R2`; optional R3/R4/R5 capabilities remain false; their routes return 404 before storage, authentication or provider work. Public config exposes `releaseScope`, `capabilities.sharedWorkspaces` and `capabilities.localGroups`. The frontend uses the returned capabilities to gate staff-workspace, local-group, journey and device controls; context and public tools retain their capability gates. Disabled integrations cannot be enabled merely by leaving old optional environment variables set. The local acceptance ledger records browser verification separately. Source/schema checks and local tests cannot prove deployed IAM, WAF behavior or hosting headers.

The script records the release scope and verifies frontend HTTP 200, CSP presence, API health, dashboard schema and disabled capabilities after publication. Its monitor smoke check now requires an actual observation timestamp no older than three hours, with current source provenance; fetching an old measurement now does not satisfy the condition. Deployed service worker install/update behavior, CORS, current admitted capacity and recovery still require cloud/browser verification.

## Cost envelope and $100 credits

Keep the existing **$15–$35/month low-traffic planning allowance** as an estimate, not a quoted Mumbai bill or a spending cap. Traffic, retained data, logs, point-in-time recovery, retries and optional resources affect charges. The user's actual credit balance, credit eligibility/expiry and account plan remain unverified.

- AWS's published [WAF examples](https://aws.amazon.com/waf/pricing/) use $5 per ACL/month, $1 per rule/group entry/month and $0.60 per million requests. One ACL with two configured entries implies roughly **$7/month before requests** at those example rates; confirm regional pricing during deployment.
- The template defines **one** provider secret. [Secrets Manager examples](https://aws.amazon.com/secrets-manager/pricing/) use $0.40/secret/month plus $0.05/10,000 API calls. Earlier two-secret planning examples do not describe this template.
- [Amplify pricing](https://aws.amazon.com/amplify/pricing/) lists static storage at $0.023/GB-month and transfer at $0.15/GB outside eligible free allowances. This script uploads a locally built static bundle. Its API's regional WAF association is separate from Amplify's optional WAF product; do not add Amplify WAF's $15/app-month fee unless that service is actually enabled.
- [API Gateway pricing](https://aws.amazon.com/api-gateway/pricing/) and current regional prices for Lambda, DynamoDB, S3 and CloudWatch should be included in the final account calculator estimate. No account bill was queried here.

At $15–$35/month, $100 mathematically covers about 2.9–6.7 months of that estimated workload before excluded charges; this is not a promise of credit duration. Configure alerts before publishing and set an explicit retention/cleanup owner. [AWS Budgets documentation](https://docs.aws.amazon.com/cost-management/latest/userguide/budgets-managing-costs.html) describes cost tracking and notifications; the current template does not configure a budget action to shut down services.

## Final deployment sequence

The cloud step is pending the final combined local acceptance gate, then the user's AWS sign-in and account/region/permissions/credit checks. Earlier passing focused checks do not replace that final combined run after the latest browser fixes. The existing OpenAQ key has already powered real local monitor checks; another provider key is not required for the current R0/R1/R2 scope. [Monitor coverage evidence](MONITOR_COVERAGE.md) records four current-city selections and Bengaluru's correctly labelled stale fallback, checked again on 11 October IST. AWS authentication should be completed through the account sign-in flow; provider keys and account credentials must remain outside chat and the frontend bundle.

1. Finish the scoped R0/R1/R2 tests, build, lint, configuration and security checks. Validate the final CloudFormation/SAM schema locally.
2. Confirm that the signed-in AWS profile belongs to the intended account and region `ap-south-1`, has the required service permissions and can use the selected plan/services. This requires the user's sign-in at the final step; no password/access key should be pasted into chat.
3. Review the concrete scoped resources, limits, retention and budget email before creating them. Transfer the existing provider key server-side only.
4. Publish the frontend/API, warm a small number of selected areas and check real source timestamps. Keep forecast-only/stale/capacity states visible where they apply.
5. Run deployed browser, offline/update, CORS/CSP, data-integrity, provider-outage and restore checks. Record the actual public URL, deployed version and measured limitations.

The code review and local checks do not guarantee zero vulnerabilities, unrestricted scaling, regulatory accuracy or cloud uptime. Remaining gates should be stated directly in the release ledger.
